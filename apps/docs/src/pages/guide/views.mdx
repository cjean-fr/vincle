# From a view to HTML

Start with a component and an HTTP response. The renderer awaits the whole
tree; you send the string.

## Set up JSX

Follow [Installation](/guide/getting-started/installation) and
[TypeScript setup](/guide/getting-started/typescript-setup) first.
The examples below live together in the same directory.

## Compose a view

Components are functions with TypeScript props. They can load their own data.

```tsx title="results.tsx"
// Replace this sample data source with your database or search service.
async function findResults() {
  return [{ title: "Getting started", href: "/guide/getting-started/installation" }];
}

export async function Results() {
  const items = await findResults();
  return (
    <ul>
      {items.map((item) => (
        <li>
          <a href={item.href}>{item.title}</a>
        </li>
      ))}
    </ul>
  );
}
```

## Return HTML from a route

Call this handler from your server's routing layer. It uses the standard
Response API; servers with their own response helpers can send the same HTML string.

```tsx
import { renderToString } from "@vincle/core";
import { Results } from "./results";

export async function GET() {
  const html = await renderToString(
    <main>
      <h1>Search results</h1>
      <Results />
    </main>,
  );

  return new Response(html, {
    headers: { "Content-Type": "text/html; charset=utf-8" },
  });
}
```

This response contains an HTML fragment. Wrap the view in your document layout
when serving a complete page.

The response waits for the complete tree. Async siblings start in document
order and overlap as soon as one awaits; their output is joined in document
order whatever the completion order.

## A whole site instead

When every visitor gets the same HTML, a server route per page is more
infrastructure than the content needs. [`@vincle/ssg`](/integration/ssg/overview)
renders a directory of pages like this one to static files at build time:
same components, same layouts, no server to run. See
[Building a static site](/guide/getting-started/first-site).

## When the page should not wait

A string response waits for the slowest component. If one query dominates the
page's time-to-first-byte, the experimental
[`@vincle/flow`](/integration/flow/overview) package can send the shell first
and patch the slow part in when it resolves. Its API tracks the declarative
partial updates specification and will change with it, so treat it as an
exploration, not a foundation.
