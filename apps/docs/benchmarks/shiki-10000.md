# Génération de 10 000 pages MDX : highlight.js et Shiki

Mesures locales du 15 octobre 2026. Trois processus neufs par configuration ; les tableaux présentent les médianes. Shiki utilise exclusivement le moteur JavaScript.

| Configuration                 | Durée de build | Pages/s | Pic RSS médian |
| ----------------------------- | -------------: | ------: | -------------: |
| highlight.js 11.12.0          |        21.57 s |     464 |        782 Mio |
| Shiki initial (deux thèmes)   |        60.16 s |     166 |       1035 Mio |
| Shiki optimisé + SSG optimisé |        36.46 s |     274 |        811 Mio |

Par rapport à Shiki initial, la version optimisée réduit la durée de **39.4 %**, augmente le débit de **65.0 %** et réduit le pic RSS médian de **21.6 %**. Elle reste **1.69 fois plus lente** que highlight.js sur ce scénario : le changement de coloriseur privilégie la qualité JSX/TSX, et ne constitue pas un gain de vitesse à lui seul.

Ce premier lot précède la mutualisation des recherches de layouts décrite plus bas.

## Scénario et périmètre

- 10 000 pages synthétiques de documentation, chacune avec un titre et des métadonnées YAML, 100 paragraphes et 3 blocs TSX d'environ 20 lignes. Les exemples comportent imports, interfaces, attributs JSX et expressions ; leur numéro de page/exemple les rend uniques.
- Pipeline réel des docs : découverte, frontmatter, Sätteri, plugins de titres/TOC, coloration, boutons de copie, rendu Core et publication. Chaque build produit effectivement **20 000 fichiers**, HTML et Markdown source.
- **Navigation/sidebar, layout du site, recherche, sitemap et assets Vite sont exclus.** Il s'agit du pipeline de contenu, pas d'un build du site complet avec 10 000 liens dans sa navigation.
- La durée commence après la génération du corpus, avant l'import de la configuration et l'initialisation du coloriseur. La suppression des fichiers de test n'est pas chronométrée. Les imports statiques du moteur SSG précèdent ce chronomètre dans les deux configurations.
- RAM : maximum entre le pic RSS du processus parent et le RSS de son arbre de processus échantillonné toutes les 25 ms. Ce n'est pas la taille du heap JavaScript. Le relevé inclut le démarrage et la préparation du corpus.
- Les répétitions sont séquentielles, sans tests/builds concurrents lancés par ce chantier. Pas de purge des caches du système, ni de verrouillage de la fréquence CPU. Les valeurs brutes permettent de voir la dispersion.
- Machine : AMD Ryzen 7 PRO 8840HS, 16 CPU logiques, environ 26,55 Gio de RAM disponible au système ; Linux x64 ; Bun 1.4.3 ; Sätteri 0.10.5 ; Shiki 4.5.0. La référence utilise le coloriseur highlight.js de `6b2629b`, avec le même harness et la même base SSG avant les optimisations de performance.

## Optimisations retenues

1. Le profil CPU sur 1 000 pages attribue environ 69 % du temps CPU échantillonné à la tokenisation TextMate. La configuration initiale tokenisait chaque bloc deux fois, pour les thèmes GitHub clair et sombre. La version finale utilise le thème Shiki à variables CSS et deux palettes dans la feuille de styles : **une tokenisation par bloc**, avec les mêmes grammaires JSX/TSX et le changement de thème sans JavaScript de coloration côté navigateur. Les palettes CSS remplacent les deux thèmes GitHub initiaux ; les nuances ne sont donc pas strictement identiques.
2. SSG consomme une copie privée du catalogue de pages dans l'ordre de découverte et libère progressivement les closures de rendu. Le catalogue fourni par l'appelant reste intact et réutilisable ; les contextes nécessaires aux plugins de publication sont conservés.
3. Le writer évite de recréer le répertoire temporaire racine déjà créé par `mkdtemp` avant chaque écriture. Les sous-répertoires continuent d'être créés normalement.

Le moteur Oniguruma et WebAssembly ne sont pas utilisés pour Shiki. `oniguruma-to-es` reste une dépendance du moteur JavaScript : il convertit la syntaxe des grammaires en expressions régulières JavaScript. Les packages importés directement sont `@shikijs/core`, `@shikijs/engine-javascript` et `@shikijs/langs` ; l'agrégateur `shiki`, les thèmes préfabriqués et highlight.js ont été retirés.

## Deuxième lot : supprimer le travail répété entre pages

Le moteur crée désormais une session de rendu par build. Les tests d'existence des fichiers `_layout.tsx`, `.jsx`, `.ts` et `.js` sont mémorisés dans cette session, y compris les absences. Dans ce corpus plat sans layout, les 10 000 pages passent de **40 000 appels de vérification à 4**. Chaque page continue de déclarer ses dépendances de layout, pour que les créations et suppressions invalident les bonnes pages en développement. Les modules restent isolés par loader et runtime JSX. Un nouveau build crée une nouvelle session ; `renderPage()` utilisé seul conserve sa session indépendante.

Les références ont été remesurées sur le code immédiatement antérieur à cette modification, déjà avec Shiki à variables CSS et les optimisations précédentes. Trois nouveaux processus par cas, mêmes paramètres et même méthode que plus haut. Les différences entre ces références et le premier lot montrent la variabilité des mesures locales ; comparer les lignes d'un même lot.

| Scénario                            |   Avant |   Après | Débit avant → après | Pic RSS avant → après |
| ----------------------------------- | ------: | ------: | ------------------: | --------------------: |
| 100 paragraphes + 3 blocs TSX       | 38.01 s | 35.32 s |   263 → 283 pages/s |         550 → 763 Mio |
| 100 paragraphes, sans blocs de code |  6.23 s |  5.33 s | 1605 → 1877 pages/s |         490 → 521 Mio |

Le gain de débit est de **7,6 % avec coloration** et **16,9 % sans coloration**. Les durées diminuent respectivement de 7,1 % et 14,5 %. Le bénéfice est limité par la tokenisation Shiki dans le scénario TSX. **Aucun gain mémoire n'est démontré** : les pics RSS médians augmentent dans ce lot. Les plages TSX sont de 537–771 Mio avant et 634–914 Mio après ; ce relevé reste sensible au ramasse-miettes et ne constitue pas une analyse de rétention du heap.

Une autre piste a été évaluée puis retirée : conserver l'ordre des producteurs, mais écrire les fichiers par lots de 16 pendant le calcul des suivants. Les trois essais donnaient 33,79 s, 296 pages/s et 912 Mio médians. Une file de 4 donnait 38,04 s et 924 Mio sur un essai. Le compromis débit/mémoire ne justifiait pas ce changement et la copie supplémentaire des buffers mutables. **Le writer final reste séquentiel.**

Les tests couvrent le retour au layout parent après suppression du layout local, l'apparition d'un layout `.jsx` au build suivant, l'isolation des loaders personnalisés et les invalidations de layouts en mode dev. La modification reste interne à SSG, sans option de configuration ni fichier de code supplémentaire.

## Reproduire la configuration finale

Depuis la racine du dépôt :

```sh
bun run --cwd packages/ssg build
bun run --cwd apps/docs bench:memory
```

Répéter la deuxième commande dans trois processus séparés. Ajouter `BENCH_CODE_BLOCKS=0` devant la commande pour le scénario sans coloration. Les paramètres par défaut sont `BENCH_PAGES=10000`, `BENCH_PARAGRAPHS=100`, `BENCH_CODE_BLOCKS=3`. `BENCH_MAX_RSS_MIB` permet d'ajouter un plafond explicite ; aucune limite mémoire n'a été imposée pendant ces mesures.

Les tests vérifient notamment la conservation du texte JSX/TSX copié, des titres de blocs et des boutons de copie, les palettes livrées dans le CSS, l'absence du coloriseur dans le bundle client, l'ordre de génération et l'immutabilité du catalogue fourni à SSG. Le build réel des 36 pages de documentation, les tests du workspace, les types, le lint et les imports/builds des packages distribués sous Bun et Node sont également vérifiés.

## Mode dev : référence du site réel avant cache incrémental

Mesures du 15 octobre 2026 sur les 38 sources du site réel (36 pages HTML), avec les layouts, la navigation, les artefacts et le serveur HTTP Vite. Ce scénario est distinct du corpus synthétique de 10 000 pages. Trois processus neufs ; chaque session comprend le démarrage, 5 reconstructions sans changement, 20 modifications successives de `privacy.mdx`, puis 3 modifications du layout racine. Les fichiers originaux sont restaurés et le serveur fermé en `finally`.

| Opération                        | Médiane |    P95 | Échantillons | Sources retraitées par opération |
| -------------------------------- | ------: | -----: | -----------: | -------------------------------: |
| Démarrage                        | 1,804 s |      — |            3 |                               38 |
| Reconstruction sans modification |  174 ms | 219 ms |           15 |                               38 |
| Modification d'une page MDX      |  155 ms | 173 ms |           60 |                               38 |
| Modification du layout racine    |  166 ms | 180 ms |            9 |                               38 |

Les reconstructions sont déclenchées par `server.rebuild()` avec le watcher automatique désactivé pour éviter les doublons. Le temps d'une modification inclut l'écriture du fichier, la reconstruction et la lecture HTTP de la page publiée. Le HTML est vérifié après chaque changement : il doit contenir le nouveau marqueur de page ou de layout. **Le debounce automatique de 75 ms, le rechargement du navigateur et son rendu ne sont pas inclus.** Il s'agit de reconstruction suivie d'un full reload, pas d'une mise à jour HMR des composants. Le démarrage inclut le chargement de la configuration et la première génération ; l'import statique initial de SSG précède le chronomètre.

Le comptage utilise un hook `metadata` déclaré incrémental et sans modification du contexte. Chaque reconstruction, même sans changement, le déclenche sur les 38 sources. L'intégration des docs utilise `discover` personnalisé et marque ses pages `incremental: false` : le cache incrémental de pages de SSG n'est donc pas utilisé. Le cache de publication évite néanmoins de réécrire les fichiers inchangés. Le cache de recherches de layouts reste actif pendant chaque reconstruction. Les tests de SSG vérifient séparément que la découverte standard réutilise les pages inchangées et ne recalcule que celles dépendant des fichiers modifiés.

| ------- | ------------------: | ---------------------------: | --------------: |
| 1       |             394 Mio |                      481 Mio |         499 Mio |
| 2       |             379 Mio |                      476 Mio |         487 Mio |

RSS du processus parent lu dans `/proc/self/status` après chaque cycle ; le pic est le maximum de ces relevés et de `resourceUsage().maxRSS`. Le RSS courant augmente sur ces sessions courtes. Aucune collecte forcée ni longue période de repos n'a été imposée : ces relevés ne permettent pas de distinguer une rétention du heap d'un effet du ramasse-miettes, et ne démontrent pas une absence de fuite.

La priorité pour accélérer le dev des docs est de rendre leur découverte compatible avec le suivi incrémental de SSG tout en invalidant correctement la navigation, les métadonnées et les artefacts globaux. Les chiffres ci-dessus ne doivent pas être extrapolés linéairement à 10 000 pages. Aucun changement du moteur dev n'a été effectué pour cette mesure.

## Mode dev : découverte personnalisée reliée au cache incrémental

Même protocole et même site réel que la référence dev précédente : trois processus neufs, chacun avec 5 reconstructions sans changement, 20 éditions de `privacy.mdx` et 3 éditions du layout racine. Aucune autre charge de test/build lancée par ce chantier pendant les mesures. Les limites de chronométrage et de RSS restent identiques : watcher automatique désactivé, appels à `rebuild()` suivis d'une lecture HTTP, sans debounce de 75 ms ni rendu navigateur.

| Opération                | Médiane avant | Médiane après | P95 après | Sources rendues après |
| ------------------------ | ------------: | ------------: | --------: | --------------------: |
| Démarrage                |       1,804 s |       1,805 s |         — |                    38 |
| Sans changement          |        174 ms |         30 ms |     43 ms |                     0 |
| Édition du contenu MDX   |        155 ms |         25 ms |     29 ms |                     1 |
| Édition du layout racine |        166 ms |        193 ms |    248 ms |                    35 |

Le temps médian d'une édition de contenu diminue d'environ **84 % (6,3 fois plus rapide)**. Le layout racine reste un changement global : toutes les pages qui le rendent sont invalidées ; les producteurs qui ne l'utilisent pas restent réutilisés. Sa reconstruction est environ 17 % plus lente dans ce lot, avec le suivi incrémental ajouté. Le démarrage est équivalent. Ces mesures portent sur les docs réelles, pas sur 10 000 pages en dev. La découverte, le calcul du catalogue et les artefacts de publication parcourent toujours le site complet.

SSG fournit maintenant un second argument à `discover(options, discover)` : cette fonction applique le cache aux handlers demandés par la découverte personnalisée. Les pages chargées indépendamment restent traitées sans réutilisation automatique. `meta.renderKey` permet d'invalider le HTML quand des données dérivées du catalogue changent. Les docs utilisent une clé commune calculée à partir de la configuration, des URL/métadonnées, des fichiers `_meta.json` et de la date de modification affichée. Le corps MDX n'entre pas dans cette clé. Des catalogues de même clé partagent leur contexte de navigation, ce qui évite d'en conserver une copie complète à chaque édition.

Une vérification supplémentaire sur le vrai serveur a confirmé :

- sans changement : 0 source rendue ;
- modification du contenu d'une page : 1 source rendue ; le HTML, le Markdown, la recherche et `llms-full.txt` contiennent le nouveau texte ;
- modification d'un titre ou d'un `_meta.json` : 38 sources rendues, artefacts et navigation mis à jour ;
- ajout d'une page : 39 sources rendues ; suppression : 38, la page disparaît aussi de la navigation et de la recherche ;
- nouvelle reconstruction sans changement après ces invalidations : 0 source rendue.

Les tests de régression vérifient aussi les dépendances enregistrées pendant le rendu d'une source réutilisée et la reprise après un échec de publication. Une entrée réutilisée est copiée dans la transaction de build : un rendu échoué ne remplace pas les sorties du dernier cache validé.
