# Streaming

Send the HTML shell immediately and stream deferred fragments inline in the
same HTTP response. One connection, progressive delivery — no client-side fetch
logic required.

## When to stream

Streaming is the right choice when:

- Time-to-first-byte matters (the shell paints before slow queries finish)
- Fragments depend on request-time data (user-specific content, live results)
- You want a single HTTP connection from shell through last fragment
- The client has no JS runtime (or you want to minimise it)

If your content is known at build time and you want zero server infrastructure,
use [Static generation](/integration/static) instead.

## renderToStream

Returns a `ReadableStream<string>`. The shell chunk is emitted first; fragment
chunks follow as they resolve. The adapter is required — pass a streaming
adapter (e.g. `NativeAdapter`) as the second argument. A ~550B polyfill is
injected only when fragments are present.

The shell is rendered fully before it is written — it arrives as a single
chunk. Fragments stream in as they resolve, each written as soon as it is
available. The response `Content-Type` is `text/html` with `chunked` transfer
encoding.

## Control reveal order with Defer.Sequence / Defer.Together

Deferred components can finish in a different order on each request.
Use `Defer.Sequence` when the page should reveal its sections in a predictable
order, or `Defer.Together` when related sections should wait for each other.

The group controls **fragment delivery**, not the order in which sibling
deferred components start their work. Their rendering can run concurrently.
Fallbacks remain part of the initial shell, and the group adds no HTML wrapper.

### Reveal in document order

`Defer.Sequence` delivers fragments in document order. If the results finish
before the summary, their patch waits until the summary can be delivered.

### Wait for related sections

`Defer.Together` holds the group's patches until all its items are ready
(or have settled after an error). This is useful when a summary and its results
should be delivered as a group.

<CodeExample src="flow/defer-together.tsx" />

For these one-shot components, suppose the summary is ready at 80 ms and the
results at 20 ms. These illustrative times describe delivery after the shell:

| Mode           | At 20 ms            | At 80 ms                                |
| -------------- | ------------------- | --------------------------------------- |
| No group       | Results patch sent  | Summary patch sent                      |
| Defer.Sequence | Results patch waits | Summary, then results patches sent      |
| Defer.Together | Results patch waits | Both patches released in document order |

If the summary finishes first, `Defer.Sequence` sends it immediately;
`Defer.Together` still waits for the results. Grouping trades earlier delivery
of some ready content for controlled reveal order. It does not guarantee a
single atomic browser paint: the adapter still applies individual patches.

### Nest groups

Groups can be nested. For example, an outer `Defer.Sequence` can reveal a
heading first, then an inner `Defer.Together` containing two related sections,
then a final fragment. The inner group must release before the outer group
advances to its next item.

A failed fragment settles its position instead of blocking later items forever.
Use Defer's `onError` to provide replacement content.

See the [component reference](/api/flow/components#defersequence--defertogether) for props.

## Node HTTP server

Pipe the stream into any Node.js `http.ServerResponse` with `for await`. Each
chunk is written as it becomes ready — the shell flushes immediately, deferred
fragments arrive as they resolve.

<CodeExample src="flow/node-server.tsx" />

The example uses `http.createServer`, but the same pattern works with
**Express**, **Fastify**, **Hono**, or any framework built on `node:http`.
The key is consuming the `ReadableStream` chunk by chunk and writing each one
to the response without buffering.

## Framework adapters

For a higher-level API, use the `serve` helper:

```tsx
import { serve } from "@vincle/flow/http";
import { NativeAdapter } from "@vincle/flow/adapters";

Bun.serve({
  port: 3000,
  fetch(req) {
    return serve(req, () => <HomePage />, NativeAdapter);
  },
});
```

`serve` builds a `Response` from a page function with optional content
negotiation (HTMX).

## Async iterables — streaming sequences

An `AsyncIterable` returned by the factory streams one patch per yielded item.
Each `yield` produces a patch; every patch from a single `<Defer>` carries
that fragment's `merge` type:

<CodeExample src="flow/stream-iterable.tsx" />

This is useful for real-time feeds, progress indicators, or any scenario where
data arrives in multiple batches. The stream stays open until the iterable
exhausts or the client disconnects.

### Driven by events, not a fixed dataset

The generator doesn't have to enumerate a known dataset — anything adaptable
into an `AsyncIterable` works, including a live event source. Node's
`events.on` turns any `EventEmitter` into one, so each event becomes its own
patch for as long as the connection stays open:

<CodeExample src="flow/stream-events.tsx" />

The factory's `signal` combines the request's abort signal with the
fragment's `timeout` — passing it to `on` stops the listener the moment
either fires, instead of leaking it for the life of the emitter.

## Merge types during streaming

| `merge`     | Effect                                    |
| ----------- | ----------------------------------------- |
| `"replace"` | Target element is replaced (default)      |
| `"append"`  | Content inserted as last child of target  |
| `"prepend"` | Content inserted as first child of target |
| `"before"`  | Content inserted as previous sibling      |
| `"after"`   | Content inserted as next sibling          |

A `<Defer>`'s `merge` applies to the whole streaming sequence — every patch from
a single `<Defer>` carries the same merge type. For a different merge per
chunk, target separate `<Defer>`s.
