# Coming from React

If you know React, you already know Vincle. The JSX is the same. Components
are functions. Props are typed. The difference is what happens **next**: no
virtual DOM, no hydration, no client runtime.

## What stays the same

| Concept                 | React                     | Vincle |
| ----------------------- | ------------------------- | ------ |
| JSX syntax              | `<div>{value}</div>`      | Same   |
| Components as functions | `function Comp({ prop })` | Same   |
| Props                   | `<Comp prop="value" />`   | Same   |
| `children`              | `{children}`              | Same   |
| Fragments               | `<>…</>`                  | Same   |
| `className` → `class`   | Auto-converted            | Same   |
| `style` objects         | `{{ color: "red" }}`      | Same   |
| TypeScript props        | `interface Props`         | Same   |

## What changes

### No client runtime

React's classic answer ships the full runtime and hydration code to the
browser for every component. Modern React narrows that with Server
Components: a component with no `"use client"` directive renders on the
server and ships no JS of its own — much like Vincle, for content that
never changes.

That exception ends the moment a component needs state. `useState` only
exists in a Client Component, so the runtime and reconciler come back,
unconditionally, no matter how small the component is. Vincle has no such
fork — every component renders the same way — and it doesn't answer
"how do I make this interactive" itself. That's delegated, in the markup,
to standard HTML or to a purpose-built client library instead of a UI
framework's runtime:

```tsx
// React — needs "use client" the moment state enters the picture; ships
// React + ReactDOM + the reconciler just to run this one counter
"use client";
export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

// Vincle — renders once; the counting is delegated to Alpine.js (a few KB,
// built for exactly this), not to a framework runtime
export function Counter() {
  return (
    <div x-data="{ count: 0 }">
      <button x-on:click="count++" x-text="count">
        0
      </button>
    </div>
  );
}
```

The two components solve the same problem, but Vincle's answer isn't "ship
less of the same kind of thing" — it's a different kind of thing
altogether: a small library scoped to this one button, not a framework
runtime scoped to the whole page.

### Async is native, not Suspense

Modern React (Server Components) lets an async component `await` directly
— much like Vincle always has, no `use()` needed for a plain top-level
fetch. What's still required is a `<Suspense>` boundary above it if you
want the shell to stream while it resolves, and a framework that
implements the RSC protocol to run any of it at all.

Vincle has no boundary and no protocol: every component can be `async`,
anywhere, with no framework requirement.

```tsx
// React Server Component — awaits directly, but still needs a Suspense
// ancestor for the fallback to stream, and a framework like Next.js to
// run it
async function Comments() {
  const data = await fetchComments();
  return <ul>{data.map(/* … */)}</ul>;
}
function Page() {
  return (
    <Suspense fallback={<Spinner />}>
      <Comments />
    </Suspense>
  );
}

// Vincle — the same shape, no boundary, no framework
async function Comments() {
  const data = await fetchComments();
  return <ul>{data.map(/* … */)}</ul>;
}
```

No `Suspense` boundaries, no fallback declarations — the `await` is the
boundary. Sibling async branches run in document order, one at a time; the
`Promise<string>` resolves when every branch finishes. (React's Client
Component pattern — reading a promise with `use()` instead of awaiting it
— still needs that same boundary, plus the promise created above it and
passed down as a prop.)

That's the default: `renderToString` simply waits. If you want the
Suspense-shaped tradeoff instead — ship the shell immediately, patch
`Comments` in once it resolves — that's opt-in via `@vincle/flow`:

```tsx
import { Template } from "@vincle/flow";

function Page() {
  return (
    <Template target="comments" fallback={<Spinner />} timeout={5000}>
      <Comments />
    </Template>
  );
}
```

By default the patch travels via a ~550 B polyfill (`NativeAdapter`).
Swap in `WebPlatformAdapter` to use the same
[WICG declarative partial updates](https://github.com/WICG/declarative-partial-updates)
proposal with no polyfill at all — on browsers that implement it natively.

### Context is scoped, not provider-based

React's `useContext` is a hook: it only works inside a component, and that
component must render as a descendant of the provider in the JSX tree. A
plain helper function can't call it, even one invoked during the same
render.

Vincle's `useContext` reads from the active `AsyncLocalStorage` scope, not
from a tree position. Anything that runs inside `withScope` can call it —
a component, a helper function, a logger — with no provider ancestor
required.

```tsx
// React — useContext only works inside a component in the provider's
// descendant tree; a plain function can't call it, even mid-render.
// React 19 renders the context itself as the provider — no `.Provider`.
function App({ user }) {
  return (
    <AuthContext value={{ user }}>
      <AuditRow action="viewed dashboard" />
    </AuthContext>
  );
}
function AuditRow({ action }: { action: string }) {
  const { user } = useContext(AuthContext); // OK — rendered inside <AuthContext>
  return (
    <li>
      {user.name} — {action}
    </li>
  );
}
function logAction(action: string) {
  const { user } = useContext(AuthContext); // invalid hook call — not a component
  console.log(`${user.name}: ${action}`);
}

// Vincle — useContext reads the active scope, so plain functions can
// call it too, as long as they run inside withScope
const Auth = context<{ user: { name: string } }>("Auth");
function logAction(action: string) {
  const { user } = useContext(Auth); // works — no component, no provider needed
  console.log(`${user.name}: ${action}`);
}

await withScope(() => {
  setContext(Auth, { user });
  logAction("viewed dashboard");
  return renderToString(<Page />);
});
```

Each `withScope` is fully isolated — concurrent renders never leak or
interfere, even when they set different context values.

### Event handlers are strings, not closures

React handlers are closures, captured automatically from the surrounding
scope. Vincle handlers are attribute strings, evaluated by the browser —
which also means Vincle never intercepts an attribute it doesn't
recognize. Nothing gets rewritten into a synthetic event system, so a
library that reads plain HTML attributes plugs straight in, with nothing
in between:

```tsx
// React — the closure needs the component, and its runtime, in the loop
const onDelete = useCallback(() => handleDelete(id), [id]);
<DeleteButton onClick={onDelete}>Delete</DeleteButton>;

// Vincle — no handler, no library, not even JavaScript: a standard HTML
// form, submitted the way forms have worked since before either framework
// existed. Forms only speak GET/POST natively, so DELETE is a route, not
// a verb
<form action={`/items/${id}/delete`} method="POST">
  <button type="submit">Delete</button>
</form>;
```

If a full navigation is more than you want, that same passthrough lets a
progressive-enhancement library swap the response in without one:

```tsx
// Vincle + HTMX — no handler to write at all. HTMX reads the attributes,
// issues the request, and swaps the response in; rendering the markup
// was the framework's whole job
<button hx-delete={`/api/items/${id}`} hx-target="#item-list" hx-swap="outerHTML">
  Delete
</button>
```

The same idea works with any attribute-driven library — Stimulus
(`data-action="click->list#delete"`), Turbo, or a hand-written
`onclick="…"` string when a dependency isn't worth it. What they share is
the mechanism: an ordinary HTML attribute, not a closure something has to
reconcile back onto the element later. A function-valued handler prop
still throws at render time on the server — there is nothing to attach it
to.

That mechanism matters most once markup arrives _after_ the first render —
a live feed, infinite scroll, a streamed fragment. A closure can't travel
inside an HTML string; injected markup has no `onClick` attached, so React
has to re-render that subtree itself, through the runtime already
hydrated on the page, to wire one back up. (The one door around that,
`dangerouslySetInnerHTML`, runs exactly Vincle's model underneath — a
plain attribute, not a closure — minus the auto-escaping.)

In Vincle, a plain attribute is live the instant the browser parses it —
first response or streamed in later, no reconciliation, no re-hydration
pass. `@vincle/flow`'s `<Template>` — the same component from the async
section above — leans on exactly this:

```tsx
import { Template } from "@vincle/flow";

async function CommentForm() {
  return (
    <form hx-post="/comments" hx-target="#comment-list" hx-swap="afterbegin">
      <textarea name="body"></textarea>
      <button type="submit">Post</button>
    </form>
  );
}

function Page() {
  return (
    <Template target="comment-form" fallback={<p>Loading…</p>} timeout={5000}>
      <CommentForm />
    </Template>
  );
}
```

Whether `CommentForm` renders in the first response or streams in seconds
later as a `<Template>` patch, HTMX picks up `hx-post` the moment the
fragment lands — the behavior never depended on a render pass to begin
with. For updates pushed from the server rather than triggered by a click,
flow's `HtmxAdapter` speaks HTMX's own out-of-band swap format directly,
so the same library handles both directions.

### Props that only meant something to the reconciler

A handful of React props are not typed at all, because nothing they talk to
exists here — there is no reconciler, no hydration, no DOM. TypeScript refuses
them at the call site rather than the renderer dropping them silently:

| React prop                                                                 | Why it is gone                              | Write instead      |
| -------------------------------------------------------------------------- | ------------------------------------------- | ------------------ |
| `ref`                                                                      | No DOM node to hold                         | —                  |
| `defaultValue`, `defaultChecked`                                           | "Initial" only means something to hydration | `value`, `checked` |
| `suppressHydrationWarning`, `suppressContentEditableWarning`               | No hydration to warn about                  | —                  |
| `radioGroup`, `autoSave`, `results`, `security`, `classID`, `unselectable` | Vendor leftovers no HTML parser reads       | —                  |

Everything else React types is kept, including the ones that do reach the
document and are easy to assume gone: `nonce`, `is`, `inputMode`, `spellCheck`,
`contentEditable`, `autoCapitalize`, and the RDFa family (`property`, `about`,
`typeof`, `vocab`, …). `key` is accepted and dropped at serialization, so a keyed
list built for React still compiles.

### No `useState`, `useEffect`, `useRef`, `useMemo`, `useCallback`

None of these exist. There is no state, no lifecycle, no re-rendering.
Every render is a fresh, deterministic function call. Where React reaches
for a hook to manage something that keeps happening _after_ the render —
a ticking clock, an interval — Vincle has nothing to reach for on the
server, so that job goes to whichever client library is already handling
interactivity elsewhere on the page:

```tsx
// React — hooks for state and effects, ticking in the browser after mount
function Timer() {
  const [time, setTime] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setTime((t) => t + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{time}s</p>;
}

// Vincle — the server renders the starting value; ticking after that is
// Alpine's job, not the framework's
function Timer({ initialTime }: { initialTime: number }) {
  return (
    <div x-data={`{ time: ${initialTime} }`} x-init="setInterval(() => time++, 1000)">
      <p>
        <span x-text="time">{initialTime}</span>s
      </p>
    </div>
  );
}
```

This one genuinely ticks — Vincle isn't reproducing the behavior with a
framework of its own, it's handing the one part that needs a client
runtime to a library built for it. React Compiler now auto-inserts most
`useMemo`/`useCallback` calls for you, which removes the boilerplate — but
it's still optimizing away re-renders that happen. Vincle has none to
optimize away in the first place, compiler or not.

## Migration checklist

| React pattern                      | Vincle equivalent                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `useState`                         | Props or context — state lives outside the render                                   |
| `useEffect`                        | Not needed — no client lifecycle                                                    |
| `useRef`                           | Not needed — no DOM access                                                          |
| `useMemo` / `useCallback`          | Not needed — no re-renders                                                          |
| `useContext`                       | `useContext` (same name, scoped instead of provider-based)                          |
| `createContext`                    | `context(key)` — typed, scoped, no provider component                               |
| `React.memo`                       | Not needed — every render is a fresh call                                           |
| `Suspense`                         | Async component + `<Template>` from `@vincle/flow`                                  |
| `ErrorBoundary`                    | No equivalent — try/catch at top level, `onError` in `@vincle/flow` for streaming   |
| `dangerouslySetInnerHTML`          | Same API — also `raw(html)` as child                                                |
| `onClick={() => fn()}`             | HTML `<form>`, `hx-*`/`data-action`/`x-on:click`, or `onclick="fn()"` (global `fn`) |
| `className` / `class`              | Both work — HTML name wins if both present, no merge                                |
| `htmlFor` → `for`                  | `htmlFor` remapped to `for`; `for` wins if both present                             |
| `@types/react`                     | Optional — install it for attribute autocomplete                                    |
| `defaultValue` / `defaultChecked`  | `value` / `checked` — nothing rehydrates, so there is no "initial" value            |
| `ref` / `suppressHydrationWarning` | Not typed — no reconciler to talk to (`@vincle/no-refs` flags them)                 |
| `<img>{caption}</img>`             | Refused — no valid HTML form; use `alt`, or a `<figure>`                            |

## What you lose

- **Hydration** — Vincle does not hydrate. If you need interactive components,
  pair it with plain HTML forms, HTMX, Turbo, Alpine.js, or a client-side
  framework
- **React ecosystem** — MUI, Radix, TanStack Table, React Router all require
  the React runtime
- **React Server Components** — not RSC-aware; use Next.js App Router for
  RSC workloads

## What you gain

- **A few KB** instead of ~140 KB — zero runtime dependencies
- **8–14× faster** than `react-dom/server` in rendering
- **Security by default** — URL scheme blocking, event handler filtering,
  content escaping — no opt-in required
- **Scoped context** — per-request isolation without provider components
- **Any runtime** — Node, Bun, Deno, Cloudflare Workers — no DOM shim needed
