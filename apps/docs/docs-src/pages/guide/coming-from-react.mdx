# Coming from React

If you know React, you already know Vincle. The JSX is the same. Components
are functions. Props are typed. The difference is what happens **next**: no
virtual DOM, no hydration, no client runtime.

## What stays the same

| Concept                 | React                     | Vincle |
| ----------------------- | ------------------------- | ------ |
| JSX syntax              | `<div>{value}</div>`      | Same   |
| Components as functions | `function Comp({ prop })` | Same   |
| Props                   | `<Comp prop="value" />`   | Same   |
| `children`              | `{children}`              | Same   |
| Fragments               | `<>…</>`                  | Same   |
| `className` → `class`   | Auto-converted            | Same   |
| `style` objects         | `{{ color: "red" }}`      | Same   |
| TypeScript props        | `interface Props`         | Same   |

## What changes

### No client runtime

React components hydrate on the client. Vincle components run once, produce
a string, and stop. There is no JavaScript shipped to the browser unless you
explicitly add it.

```tsx
// React — ships React runtime + component code to browser
export function Page() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

// Vincle — renders HTML once, zero JS shipped
export function Page() {
  return renderToString(<button onclick="let c=0;this.onclick=()=>this.textContent=++c">0</button>);
}
```

### Async is native, not Suspense

React requires `Suspense` boundaries and a streaming API for async data.
Vincle lets any component be `async` directly:

```tsx
// React — the promise is created above the boundary and passed down;
// use() cannot take a promise created fresh in the same render
function Page() {
  const commentsPromise = fetchComments();
  return (
    <Suspense fallback={<Spinner />}>
      <Comments commentsPromise={commentsPromise} />
    </Suspense>
  );
}
function Comments({ commentsPromise }) {
  const data = use(commentsPromise);
  return <ul>{data.map(/* … */)}</ul>;
}

// Vincle — just async, no boundary, no promise plumbing
async function Comments() {
  const data = await fetchComments();
  return <ul>{data.map(/* … */)}</ul>;
}
```

No `Suspense` boundaries, no fallback declarations — the `await` is the
boundary. Sibling async branches run in document order, one at a time; the
`Promise<string>` resolves when every branch finishes.

### Context is scoped, not provider-based

React's `useContext` is a hook: it only works inside a component, and that
component must render as a descendant of the provider in the JSX tree. A
plain helper function can't call it, even one invoked during the same
render.

Vincle's `useContext` reads from the active `AsyncLocalStorage` scope, not
from a tree position. Anything that runs inside `withScope` can call it —
a component, a helper function, a logger — with no provider ancestor
required.

```tsx
// React — useContext only works inside a component in the provider's
// descendant tree; a plain function can't call it, even mid-render
function AuditRow({ action }: { action: string }) {
  const { user } = useContext(AuthContext); // OK — rendered inside <AuthProvider>
  return <li>{user.name} — {action}</li>;
}
function logAction(action: string) {
  const { user } = useContext(AuthContext); // invalid hook call — not a component
  console.log(`${user.name}: ${action}`);
}

// Vincle — useContext reads the active scope, so plain functions can
// call it too, as long as they run inside withScope
function logAction(action: string) {
  const { user } = useContext(Auth); // works — no component, no provider needed
  console.log(`${user.name}: ${action}`);
}

await withScope(() => {
  setContext(Auth, { user });
  logAction("viewed dashboard");
  return renderToString(<Page />);
});
```

Each `withScope` is fully isolated — concurrent renders never leak or
interfere, even when they set different context values.

### Event handlers are strings, not closures

React handlers are closures — a new function identity on every render,
which is why passing one to a memoized child needs `useCallback` to keep
that identity stable. Vincle has no re-renders to begin with: a handler is
just an HTML attribute string, identical every time.

Untrusted values never belong inside the handler string itself. They travel
through a regular attribute instead — auto-escaped like any other — and the
handler reads them back at runtime:

```tsx
// React — a fresh closure every render; useCallback exists specifically
// to give it a stable identity so memoized children don't re-render
const onDelete = useCallback(() => handleDelete(id), [id]);
<DeleteButton onClick={onDelete}>Delete</DeleteButton>;

// Vincle — id travels through an auto-escaped attribute, not through the
// handler string; the handler itself never changes
<button data-id={id} onclick="handleDelete(this.dataset.id)">
  Delete
</button>;
```

A function-valued handler throws — there is nothing to attach it to, so the
render fails rather than emit a button whose handler does nothing. The
handler string is HTML-escaped, but the JavaScript inside it is not — which
is exactly why untrusted data belongs in an attribute (as above), never
interpolated directly into the string.

### No `useState`, `useEffect`, `useRef`, `useMemo`, `useCallback`

None of these exist. There is no state, no lifecycle, no re-rendering.
Every render is a fresh, deterministic function call.

```tsx
// React — hooks for state and effects
function Timer() {
  const [time, setTime] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setTime((t) => t + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{time}s</p>;
}

// Vincle — the time is whatever it is at render time
function Timer({ time }: { time: number }) {
  return <p>{time}s</p>;
}
```

## Migration checklist

| React pattern             | Vincle equivalent                                                                 |
| ------------------------- | --------------------------------------------------------------------------------- |
| `useState`                | Props or context — state lives outside the render                                 |
| `useEffect`               | Not needed — no client lifecycle                                                  |
| `useRef`                  | Not needed — no DOM access                                                        |
| `useMemo` / `useCallback` | Not needed — no re-renders                                                        |
| `useContext`              | `useContext` (same name, scoped instead of provider-based)                        |
| `createContext`           | `context(key)` — typed, scoped, no provider component                             |
| `React.memo`              | Not needed — every render is a fresh call                                         |
| `Suspense`                | Async component + `<Template>` from `@vincle/flow`                                |
| `ErrorBoundary`           | No equivalent — try/catch at top level, `onError` in `@vincle/flow` for streaming |
| `dangerouslySetInnerHTML` | Same API — also `raw(html)` as child                                              |
| `onClick={() => fn()}`    | `onclick="fn()"` as string                                                        |
| `className` / `class`     | Both work — HTML name wins if both present, no merge                              |
| `htmlFor` → `for`         | `htmlFor` remapped to `for`; `for` wins if both present                           |
| `@types/react`            | Optional — install it for attribute autocomplete                                  |

## What you lose

- **Hydration** — Vincle does not hydrate. If you need interactive components,
  pair it with HTMX, Turbo, Alpine.js, or a client-side framework
- **React ecosystem** — MUI, Radix, TanStack Table, React Router all require
  the React runtime
- **React Server Components** — not RSC-aware; use Next.js App Router for
  RSC workloads

## What you gain

- **A few KB** instead of ~140 KB — zero runtime dependencies
- **8–14× faster** than `react-dom/server` in rendering
- **Security by default** — URL scheme blocking, event handler filtering,
  content escaping — no opt-in required
- **Scoped context** — per-request isolation without provider components
- **Any runtime** — Node, Bun, Deno, Cloudflare Workers — no DOM shim needed
